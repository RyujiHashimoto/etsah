# 人材派遣の基幹を PROUT で書く

対象は、人材派遣会社の基幹で繰り返す部分である。スタッフ、派遣先と案件、マッチング、個別契約と就業条件、勤怠と派遣先承認、請求と給与、粗利。抵触日は仕様に書いた派遣期間から計算し、36協定の上限はスロットである。一般則の天井（月45時間、年360時間、特別条項は年720時間、時間外+休日は月100時間未満、2〜6か月平均80時間、月45時間超は年6回）を超える設定はエラーにする。この天井は法令意見ではなく、社労士の確認が要る。判断が分かれるところはこの文書に残す。

`prout.py` は変更していない。契約層の検証器は別途編集されているため、日付と小数単価の検査はパターン層に置いた。

## 今の言語で既に書けること

### 契約層

`examples/staffing.prout` は、今の検証器だけで次を表現する。

- 請求単価 >= 支払単価。両方を `Int`（整数円）にすると、`1500 >= 1800` は `E-PRE` で落ち、`2800 >= 1800` は静的に通る。
- 終了日 <= 抵触日。両方を `Int`（1970-01-01 からの通算日）にすると、同じ線形算術で判定できる。2026-04-01 は 20544、2029-04-01 は 21640。
- 派遣先承認。`Bool` の `client_approved == true`。`false` は `E-PRE`。
- 請求額の式。`Money * Int` は `Money` になる。`invoice_amount` の `impl rate * hours` は型が付く。
- 効果。月次締めは `read(contracts)`、`write(invoices)`、`write(payroll)`、`emit(audit)` と一致しなければならない。
- 保存済みの契約を読む flow は、フィールド比較を証明できない。`W-PRE` の実行時ガードが3件残り、エラーは0件で終了する。

ネットワークの許可リスト（既定は `stripe`）と、効果の過不足もそのまま使える。

### パターン層

基幹の器は、既存のパターンでかなり組める。

| 業務 | 既存パターン |
|---|---|
| ログインとロール（コーディネーター、派遣先、給与、スタッフ） | `auth` |
| スタッフ・案件の一覧と登録 | `crud` |
| 名前とスキル欄の検索 | `search` |
| 履歴書 | `upload` |
| 請求額・給与・粗利の画面 | `dashboard` |
| 派遣先への提出通知 | `notify` |
| 社内の申請→承認→差し戻し | `approval` |

`approval` は汎用の状態遷移であり、勤怠の「派遣先が承認するまで請求しない」、個別契約の抵触日、請求単価と支払単価の関係は知らない。

## ギャップ

契約層には次が無い。試作範囲にも「時間は対象外」「線形算術の事前条件のみ」と書いてある。

1. **日付。** `2026-04-01` は字句の上では `2026 - 4 - 1` になる。`Date` 型も日付リテラルも無い。文字列の `<=` は型検査は通るが、値は実行時ガードのままである。
2. **小数の時間単価。** 字句は整数だけを数値にする。`1.2` は `tests/test_lexer.py` が拒否する。`SPEC.md` は `1/2` の意味が言語ごとに衝突する、という理由で一つの除算の意味を決めていない。
3. **金額リテラル。** `Money` は不透明型で、整数との比較と `Money * Int` はできる。しかし `Money` の引数に `2800` を渡すと `E-TYPE` になる。整数から `Money` を作るには `yen(amount: Int) -> Money` のような op を自分で宣言する。
4. **期間。** 時刻の差、時間と分、月の営業日は無い。
5. **コレクション。** スキルの包含は実行時ガードに落ちる。マッチングの中身は証明できない。
6. **パターン層の型。** `requires_fields` はフィールド名だけを見る。`refund` は `status: String` と書くが、ショップの仕様は `OrderStatus` のまま通る。

## 方針

契約層の字句と線形算術には手を入れない。日付・期間・小数単価はパターンコンパイラのスロットとフィールド型として足し、マニフェストの `constraints` と `patterns/staffing_rules.py` で仕様時に比較する。協定の上限そのものはスロットである。一般則の天井だけを、既定値と「それを超えたらエラー」の境界としてコンパイラに置いている。

検査できないものは `custom` と `notes` に残し、エラーメッセージとこの文書で「検査していない」と書く。

## 追加したパターン

五つとも `patterns/examples/staffing.prout`（基幹）、`patterns/examples/staffing_desk.prout`（短期案件）、`patterns/examples/staffing_limits.prout`（うるう日・クーリング・通算）でビルドが通る。エラーは0である。

### `timesheet`

勤怠の提出と派遣先承認。`approver` は必須なので、承認ロールの無い勤怠は `E-SLOT` になる。状態は `draft → submitted → client_approved`、差し戻しは `returned`。`overtime_cap_hours` は `Duration`（`45` や `7h30m`）。非負でない文字列はスロットエラーになる。

`overtime_hours` フィールドがあるか、`overtime_cap_hours` が正なら、同じ仕様にその勤怠を指す `overtime_agreement` が要る。無いと `E-POLICY`。月次（`period` の既定）の cap は、特別条項が無いとき一般則の月45時間を超えられない。日次の cap は月45時間と比べない。`staffing_desk` の `7.5` は日次の設定であり、法定の1日の上限ではない。

実労働時間と上限の比較は、コンパイラは走らせない。実行時に何を比べ、警告と停止のどちらにするかは、次のパターンが生成する。

### `overtime_agreement`

36協定の上限。必須は、協定エンティティ、対象の勤怠、`warn_at_hours`、`on_warning`、`on_limit`。`on_warning` は `notify`（通知し、提出は止めない）。`on_limit` は `reject`（提出を止める）。警告閾値は、硬停止の月上限より小さくなければならない。

省略した上限は一般則を既定にする。書いた値が天井を超えると `E-POLICY`。

| スロット | 既定 | 天井 | いつ効くか |
|---|---|---|---|
| `monthly_overtime_hours` | 45 | 45時間以下 | 常に |
| `yearly_overtime_hours` | 360 | 360時間以下 | 常に |
| `special_clause` | `none` | `none` または `enabled` | 常に |
| `special_yearly_overtime_hours` | 720 | 720時間以下 | `enabled` のとき |
| `month_with_holiday_hours` | 省略時は100時間未満 | 0より大きく100未満 | `enabled` のとき |
| `average_hours` | 80 | 80時間以下 | `enabled` のとき |
| `months_over_limit` | 6 | 6回以下 | `enabled` のとき |

`special_clause` が `none` のときに特別条項のスロットを書くとエラーになる。年の上限が月の上限を下回る値もエラーになる。特別条項を付ける勤怠エンティティには `holiday_hours: Duration` が要る。無いと、休日労働を0にして100時間未満を通してしまう。

変形労働時間制の42時間・320時間、自動車の運転業務、医師、研究開発、災害時の建設事業は天井を分けていない。それらの事業で法定より高い値を書くと、このコンパイラはエラーにする。

### `dispatch_contract`

個別契約。スタッフ、派遣先、開始日、終了日、通知された抵触日が必須。エンティティには `duties` と `workplace` を要求する。これは就業条件明示の全文ではない。

検査は次である。

- `start_date <= end_date`
- `end_date <= conflict_date`（通知された日。抵触日当日も通す）
- 計算した抵触日。通知日と同じなら、終了日の判定は上の比較に任せる。計算した日の方が早く、終了日がそれを超えるなら `E-POLICY`
- 通知日と計算日が違えば `W-POLICY`。通知日は上書きしない

計算は `patterns/staffing_rules.py` の `datetime` で行う。`prout.py` は触っていない。

抵触日は、起算日の3年後の応当日である。これは「3年の期間が満了する日の翌日」で、応当日がある日は応当日そのものになる。2026-04-01 の起算なら 2029-04-01。2015-09-30 なら 2018-09-30。応当日が無い 2024-02-29 は、満了日を2027-02-28とし、抵触日を 2027-03-01 にする。

起算日は二つある。

- 事業所単位。同じ `office` の契約と `office_history`（`YYYY-MM-DD/YYYY-MM-DD` のカンマ区切り）のうち、クーリングで切れていない連続期間の最も早い開始日。`office` を省くと、その契約と自分の history だけを見る。
- 個人単位。同じ `person` と `org_unit`、および `person_history`。片方だけ書くと `E-SLOT`。`conflict_date` と比べるのは事業所単位の計算値である。個人単位の通知日は任意の `person_conflict_date`。個人単位の計算日の方が早く、終了日がそれを超えるときも止める。

クーリングは、前の終了日の翌日から数えて3か月を超える空白（3か月+1日）で起算をリセットする。2026-03-31 に終わり、次が 2026-07-01 なら継続、2026-07-02 ならリセットする。空白がちょうど3か月のときはリセットしない。

`exempt` が `indefinite`（無期雇用）、`age60`（60歳以上）、`day_limited`（日数限定）、`leave_substitute`（産前産後・育児・介護休業の代替）のとき、抵触日を超えてもエラーではなく `W-POLICY` になる。メッセージに "not a legal opinion" を付ける。`day_limited` と `leave_substitute` はフラグがあるだけで、勤務日数や休業の事実は見ない。有期プロジェクトはフラグにしていない。`none` のまま超えていれば `E-POLICY`。

### 静的検査と実行時検査

コンパイラが今判定するのは、仕様に書いた定数だけである。実績の時間と、データベースに後から入る契約は見ない。

静的（仕様。今エラーまたは警告にする）:

- 協定の各上限が一般則の天井以内か。特別条項のスロットが、条項を有効にしたときだけ書かれているか
- 警告閾値が硬停止の月上限より前か。`on_warning` と `on_limit` が指定されているか
- 時間外のある勤怠に、その勤怠を指す協定があるか
- 仕様の span から抵触日を計算し、終了日と通知日と比べるか

実行時（生成するだけで、このコンパイラは走らせない）:

- 月の時間外が `warn_at_hours` 以上かつ月上限以下なら `notify`。月上限を超えたら `reject`
- 年の時間外合計が年上限を超えたら `reject`
- 特別条項では、年720（または設定値）、時間外+休日の月上限、2・3・4・5・6か月の各平均、月上限超過が年6回（または設定値）を、同じ `reject` で止める。月上限ちょうどは「超えた月」に数えない。100時間ちょうどは「100時間未満」に反する
- 保存された契約から、同じ事業所・同じ人と組織単位で抵触日を再計算する。通知日と違えば警告し、通知日は残す

`proutc build` は、この区別を標準出力と `manifest.json` の `runtime_checks` に出す。`phase` が `static` の行は仕様の評価、`runtime` の行は生成した検査である。レポートの `lib/labor/overtime_checks.ts` と `lib/labor/conflict_date.ts` は、その説明を成果物の行として数える。実ソースはまだ書き出さない。

### `staffing_billing`

請求と給与。`bill_rate` と `pay_rate` は `Rate`（非負の十進数）。`bill_rate >= pay_rate` を仕様時に見る。等しい単価は通す。`1800.50` と `1800.5` は同じ値である。

同じ仕様に `timesheet` が無いと `E-POLICY`（勤怠の派遣先承認が無い）になる。社会保険、雇用保険、割増、交通費は引かない。差が非負でも、それらを引くと赤字になり得る。この検査は同一労働同一賃金の充足ではない。

### `matching`

スタッフのスキル欄と案件の必須スキル欄が存在することを見る。省略した `required_skills` スロットは、案件エンティティの `required_skills` フィールドを既定にする。スキルの中身が案件を満たすかは見ない。

## 壊した例

`patterns/examples/staffing_broken.prout` はパターン検査が4件で落とす。

1. 終了日 `2029-04-02` が通知された抵触日 `2029-04-01` の後。開始が `2026-04-01` なので計算値も同じ日で、終了日のエラーは従来の比較が1件出す
2. `timesheet` に `approver` が無い
3. 請求単価 `1500` が支払単価 `1800.50` を下回る
4. `overtime_hours` があるのに `overtime_agreement` が無い

`patterns/examples/staffing_limits_broken.prout` は、上限と計算した抵触日で落とす。エラー7、警告1。

- 月50時間、特別条項の年721時間、時間外+休日100時間、月45時間超が年7回
- もう一つの勤怠に時間外があり、協定が無い
- `2024-02-29` 開始の終了 `2027-03-02` が抵触日 `2027-03-01` の後
- `2024-04-01` から通算した事業所の抵触日は `2027-04-01`。終了 `2027-04-02` はそれを超える。通知した `2029-04-01` は計算値と違うので警告にもなる。通知日だけ見ればこの終了日は通ってしまう

`examples/staffing_broken.prout` は契約検査が3件の `E-PRE` で落とす。整数円 `1500 >= 1800`、通算日 `21641 <= 21640`、`false == true`。

## 提案したが実装していないこと

契約層の変更案である。`prout.py` には入れていない。

1. **`Date` と比較。** リテラルは引用符付きの `d"2026-04-01"` のように、減算と衝突しない形が要る。暦日の `<=` は整数の通算日に落として、今の線形算術を再利用できる。タイムゾーンは日付だけなら不要。
2. **`Duration`。** 日数の差 `end - start` を `Int` で返す。時間の小数は、除算の意味が未決なので、分単位の整数にしてから契約層に載せる方が衝突が少ない。
3. **小数の `Rate`。** 字句に `1.2` を足すと `tests/test_lexer.py` と `SPEC.md` の「一つの除算の意味を決めない」に触れる。パターン層は十進数として比較している。契約層へ移すなら、円の小数2桁を整数の銭として持ち、リテラルだけを十進数に見せる固定小数が、線形算術を壊さない。
4. **`Money` の整数リテラル。** `2800` を `Money` として渡せるようにするか、`yen` を組み込み op にする。今は仕様側の op で代用している。
5. **実労働時間 <= 協定上限** を契約の `pre` にする。パターン層は実行時検査の文章を生成するだけで、実績時間は判定しない。45 や 360 を契約層の検証器は知らない。
6. **スキル包含。** 集合の契約は、仕様が実行時ガードと明記している。マッチングの中身はそこに残す。
7. **`requires_fields` の型検査。** 今やると `status: String` と `OrderStatus` の既存仕様が落ちる。新しい `field_types` だけを厳密にした。
8. **勤怠の操作デモ。** `demo.html` は `approval` 専用のままである。`timesheet` の状態遷移も同じ機構で出せるが、今回は生成していない。

## 法令として扱っていることと、扱っていないこと

計算と天井は入れた。どれも法令意見ではない。社労士が数字と起算を確認する前提である。

扱っているのは、仕様に書いた日付と上限だけである。

- 抵触日は、事業所単位と個人単位のそれぞれで、連続する派遣の最も早い開始日に3年を足した日。2月29日で応当日が無い年は3月1日。空白が3か月+1日以上なら起算をリセットする。通知日は残し、計算日と違えば警告する。
- 36協定は、一般則の天井を既定と上限にする。警告は `notify`、上限超過は `reject`。実績時間の判定は実行時の生成物に残す。

扱っていないのは次である。

- 期間制限の例外の認定。`day_limited` と `leave_substitute` は警告に下げるフラグで、日数（通常の労働者の半分かつ10日以下）や休業の事実は見ない。有期プロジェクトはフラグにしていない。無期雇用と60歳以上を警告に下げることも、適用を認定したことにはならない。
- 36協定の一般則以外。1年単位の変形労働時間制（月42時間、年320時間）、自動車の運転業務、医師、研究開発、災害時の建設事業は天井を分けていない。
- 抵触日当日を終了日に含めてよいか。今の比較は `end_date <= 抵触日` で、当日も通す。抵触日を「受け入れできない最初の日」と読むなら、終了日は前日までである。
- 同一労働同一賃金（派遣先の通常の労働者との均衡・均等）。請求単価と支払単価の大小は、その判定ではない。比較対象の賃金台帳はエンティティにしていない。
- 社会保険・雇用保険の加入要件、料率、標準報酬月額。年度と事業所で変わるため `custom` に残した。`insured` は文字列であり、加入判定はしない。
- 割増賃金の率、深夜・休日、通勤手当。粗利の式に入れていない。
- 就業条件明示の必須記載の全文。業務と就業場所だけをフィールド名で要求している。

## オーナーへの質問

1. 契約層の `Date` は、通算日への落とし込みでよいか。リテラルの形は `d"2026-04-01"` で減算と分ける想定でよいか。
2. 小数単価は、契約層では銭の整数、パターン層では十進数、の二段のままでよいか。字句に小数を足す変更は、今の `1.2` を拒否するテストと衝突する。
3. 抵触日の例外は `indefinite` と `age60` に、任意フラグの `day_limited` と `leave_substitute` を足した。警告のまま人が見る形でよいか。有期プロジェクトはまだフラグにしていない。
4. 36協定は、会社の協定値をスロットにし、一般則を既定かつ天井にした。以前の「既定値にしない」は撤回している。変形労働時間制や適用除外を天井から外したままでよいか。
5. 同一労働同一賃金を、次のパターン（比較対象の賃金を持つエンティティ）にするか、`custom` のままにするか。
6. 社会保険の料率テーブルをスロットにするか。今回は年度で変わるものとして外した。
7. パターンは「同じ形が二度出てから入れる」が、派遣の四つは基幹仕様と短期デスク仕様から、`overtime_agreement` は基幹・短期・期間計算の三例から入れた。この追加でよいか。
8. `requires_fields` を型検査に昇格させるか。既存仕様の `OrderStatus` をどう扱うかが先に要る。
9. 抵触日は「3年の期間の翌日」で、応当日がある日は応当日そのもの（2026-04-01 → 2029-04-01）。2024-02-29 は 2027-03-01。この読みでよいか。
10. `end_date <= 抵触日` は抵触日当日を通す。当日を禁止するなら、比較を `<` に変える。どちらにするか。
11. クーリングは、前の終了の翌日から3か月を超えた日（2026-03-31 終了なら 2026-07-02 開始）でリセットし、ちょうど3か月（2026-07-01）は継続にした。空白の数え方はこれでよいか。指針が避ける「制限回避のためのクーリング」も、日付が空いていればリセットする。止めない判断でよいか。
12. 必須の `conflict_date` は事業所単位の計算値と比べる。個人単位は、計算日の方が早いときだけ終了日を止め、通知との警告は任意の `person_conflict_date` に限る。通知スロットを「早い方」と比べる形に変えるか。
13. `leave_substitute` は産前産後・育児に加え、介護休業の代替も含めた。分けるか。
14. 時間外+休日は、スロットを省くと実行時に「100時間未満」（100ちょうどで `reject`）。スロットに 99 と書くと 99 を超えたら `reject` で、99.5 は通らない。この違いでよいか。警告閾値は法定ではなく、仕様が必ず書くスロットのままか。
